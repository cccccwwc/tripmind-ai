## 评测范围

- 从版本化的 30 条旅行需求数据集中顺序抽取前 10 条。
- 覆盖北京、成都、杭州、上海、西安、青岛、广州、深圳、南京和苏州。
- 每条样本都真实调用本地 FastAPI、DeepSeek、地图检索、天气、酒店节点和 LangGraph 行程工作流，没有使用业务结果 Mock。
- 使用确定性规则评估全部 10 条，并对前 3 条增加 LLM-as-judge 抽检。
- 运行记录仅发布聚合指标和脱敏逐样本分数，不包含 API Key、完整第三方响应或用户隐私数据。

## LLM-as-judge 抽检

前 3 条样本的语义质量平均分为 **31.67%**。评审指出的主要问题是：

1. 个别 POI 类型不适合作为景点，例如寄存处、公交站或建设中场馆。
2. 某些跨区移动仍使用固定的 30 分钟交通时间，路线可执行性不足。
3. 成都避开火锅的约束在最终餐饮安排中没有被完全遵守。
4. 行程说明存在模板化，开放信息和历史文化讲解不够具体。

因此，“结构化正确”和“用户实际可执行”被明确分开评估。下一轮优化应加入 POI 类型白名单/黑名单、真实路线耗时、避雷约束终检，并在修复后重跑相同 10 条样本。

## Token 与成本口径

当前业务接口尚未汇总各内部模型调用的供应商 `usage`，报告中的 Token 为评测器估算值。成本按 [DeepSeek 官方价格](https://api-docs.deepseek.com/quick_start/pricing/)中的 `deepseek-flash` 高峰价格上界估算：未缓存输入 `$0.30 / 1M tokens`、输出 `$1.20 / 1M tokens`；高德和 Tavily 的配额成本未计入。LLM-as-judge 的消耗不计入业务任务成本。

## 可复现命令

```bash
cd backend
source .venv/bin/activate
python -m evals.runner \
  --live --confirm-live --limit 10 \
  --base-url http://127.0.0.1:8000 \
  --judge-sample 3 \
  --input-cost-per-million 0.30 \
  --output-cost-per-million 1.20
```

真实运行会消耗第三方 API 配额；评测器默认要求同时传入 `--live --confirm-live`，防止误调用。
